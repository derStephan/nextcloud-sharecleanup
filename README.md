# Share Cleanup

[![Tests](https://github.com/derStephan/nextcloud-sharecleanup/actions/workflows/tests.yml/badge.svg)](https://github.com/derStephan/nextcloud-sharecleanup/actions/workflows/tests.yml)
[![codecov](https://codecov.io/gh/derStephan/nextcloud-sharecleanup/branch/main/graph/badge.svg)](https://codecov.io/gh/derStephan/nextcloud-sharecleanup)

A Nextcloud app that **automatically ends file shares** after a configurable period
(default: **365 days**) — covering internal user/group shares as well as external
link, email, federated, Talk, Deck and any future share types.

**The files themselves are never deleted — only the share is removed.**

> in collaboration with the repository owner. It is provided as-is — please review
> and test it on a staging instance before using it in production.

**Repository:** <https://github.com/derStephan/nextcloud-sharecleanup>

## What it does

When a user shares a file or folder, Share Cleanup:

1. **Tags the file** with a system tag showing the share's end date
   (e.g. `Share ends on 2027-08-15`). One tag per end date — multiple shares
   ending on the same day share a single tag.
2. **Notifies the sharing user** when 90 % of the lifetime has passed
   (i.e. 10 % before the share ends). At 365 days that's day 328 —
   roughly five weeks of advance warning.
3. **Ends the share** once it reaches the configured maximum age.
4. **Cleans up tags** automatically: any tag whose date has passed is deleted
   on the next run.

## Features

| Feature | Details |
|---|---|
| **All share types** | User, group, link, email, federated, circle, Talk room, Deck — plus **future types detected automatically** from the database |
| **Configurable lifetime** | Default 365 days, adjustable 1–3650 (admin settings or OCC) |
| **Advance notification** | At 90 % of lifetime, once per share, via Nextcloud notification |
| **File tagging** | System tag `Share ends on YYYY-MM-DD` at share creation |
| **Expiration-date protection** | Shares with their **own expiration date are never touched** — not tagged, not notified, not ended |
| **Dry-run mode** | Enabled by default — log only, change nothing, until you're ready |
| **OCC command** | `occ sharecleanup:run [--days=N] [--dry-run] [--force]` |
| **20 languages** | UI and notifications fully translated (de, en, es, fr, zh, hi, ar, pt, ru, ja, ko, it, tr, pl, nl, vi, id, uk, sv, el) |
| **Hourly background job** | Registered automatically on app enable — no cron setup needed |

## Requirements

- **Nextcloud 33 or higher**
- Background jobs set to **Cron** (Administration → Basic settings) — the Nextcloud default
- System tags enabled (Nextcloud core feature, on by default)

## Installation

```bash
# Extract into your Nextcloud apps directory
tar -xzf sharecleanup-1.2.1.tar.gz -C /var/www/nextcloud/apps/

# Set ownership (adjust user for your setup)
chown -R www-data:www-data /var/www/nextcloud/apps/sharecleanup

# Enable the app
sudo -u www-data php /var/www/nextcloud/occ app:enable sharecleanup
```

## Configuration

**Administration → Sharing → Share Cleanup**

| Setting | Default | Description |
|---|---|---|
| **Maximum share age (days)** | 365 | Shares older than this are ended automatically |
| **Dry-run mode** | Enabled | Log only, change nothing — disable when ready |

## Usage

### Automatic

The app runs **hourly** via a Nextcloud background job. No configuration needed.

### Manual

```bash
# Dry run (default) — see what would happen
sudo -u www-data php occ sharecleanup:run --dry-run

# Live run — actually end shares
sudo -u www-data php occ sharecleanup:run --force

# Custom max age
sudo -u www-data php occ sharecleanup:run --days=30 --force
```

## How it works

```
Day 0        Share created → File tagged with "Share ends on YYYY-MM-DD"
Day 328      90 % of lifetime → User notified (once per share)
Day 365      100 % of lifetime → Share ended automatically
```

## Security

- All database access uses the Nextcloud **QueryBuilder** — no raw SQL, no user input in queries
- Settings endpoint protected by `#[AuthorizedAdminSetting]` — full admin role required
- Notification content is server-side escaped by the Nextcloud notification API
- No external network calls, no third-party dependencies

## Running the tests

The app ships PHPUnit unit tests for its core logic (see `tests/`):

```bash
composer install
vendor/bin/phpunit
```

The tests run standalone (with minimal OCP stubs) or inside a Nextcloud
checkout (using the real OCP interfaces). See `tests/README.md` for details.

### Continuous integration

GitHub Actions run the checks automatically on every push and pull request
(see `.github/workflows/`):

* **Lint** — PHP syntax check across PHP 8.1–8.4
* **PHPUnit** — unit tests with OCP stubs, across PHP 8.1–8.4
* **Integration** — unit tests against a real Nextcloud server checkout
  (currently `stable33` and `stable34`)
* **App info** — validates `appinfo/info.xml`
* **Code coverage** — uploads coverage to [Codecov](https://codecov.io/gh/derStephan/nextcloud-sharecleanup)
  on every push to `main`

**Concurrency:** On pull requests, new pushes cancel in-progress runs to
save resources. On `main`, runs always complete — this ensures the
bump-nextcloud workflow can react to green test results.

### Automatic Nextcloud version tracking

A scheduled workflow (`bump-nextcloud.yml`) checks **weekly** (or manually
via `workflow_dispatch`) for new Nextcloud server releases. When a new major
version is published (e.g. NC 35):

1. `appinfo/info.xml` — `max-version` is bumped to the new version
2. `.github/workflows/tests.yml` — the integration test matrix is updated
   to test against the **previous and the new stable version**
   (e.g. `stable34` + `stable35`, dropping `stable33`)
3. Both changes are committed and pushed automatically with `[skip ci]`
   to avoid triggering a new test run

This means the app always declares compatibility with the latest Nextcloud
release and tests against it — no manual intervention needed.

### Release process

Releases are **gated behind green tests**: the release workflow
(`release.yml`) only runs after the test workflow completes successfully.
If any test fails, no release is created.

Releases are **semantic**: the workflow analyzes commit messages since the
last tag (`feat:` → minor, `fix:` → patch, `BREAKING CHANGE` / `!:` → major),
updates the version in `info.xml`, builds a tarball, creates a Git tag,
and publishes a GitHub Release with the archive attached.
